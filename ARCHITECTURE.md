# Архитектура DzenAnalytics

Как устроено приложение изнутри: где живут данные, как они приходят из
Дзен-мани и уходят обратно, из чего собран интерфейс, как это тестируется и
собирается. Документ для тех, кто правит код; что умеет сервис — в
[README](README.md) и в справке внутри приложения.

## В двух словах

- **Чистое SPA без своего бэкенда.** React 19 + TypeScript + Vite, стили —
  Tailwind, состояние — Zustand, графики — Recharts. Всё работает в браузере.
- **Данные — у пользователя.** Операции, справочники, настройки и токен лежат в
  IndexedDB браузера. С Дзен-мани браузер говорит напрямую
  (`api.zenmoney.ru`), курсы ЦБ берёт с `cbr-xml-daily.ru`. Других сетевых
  запросов у приложения нет.
- **Два источника:** подключение к API Дзен-мани (синхронизация в обе стороны)
  или CSV-выгрузка из приложения (только чтение).
- **Три способа запуска:** обычная сборка (`dist/`, её отдаёт любой
  статический сервер или Docker-образ), однофайловая (`DzenAnalytics.html` —
  двойной клик, без сервера) и онлайн-версия.

## Папки

```
src/
├── main.tsx      вход: выбор роутера, разбор возврата после входа, демо, service worker
├── App.tsx       оболочка: маршруты, глобальные окна, гидратация сторов, фоновые таймеры
├── types.ts      Transaction и базовые типы
├── pages/        разделы — по файлу на маршрут (31 раздел)
├── components/   интерфейс; общие компоненты — здесь же (см. «Общие компоненты»)
├── hooks/        React-хуки, которые собирают данные из сторов для разделов
├── store/        Zustand-сторы: данные, правки, настройки (~80)
├── lib/          чистая логика без React: расчёты, отображение API, отправка, выгрузки
└── test/         общие заготовки для тестов (tx(), курсы)
e2e/              Playwright-тесты и поддельный Дзен-мани
scripts/          выпуск: архив, текст релиза, тексты лицензий
docker/           Dockerfile, nginx.conf, docker-compose
public/           sw.js, manifest, иконки
```

Правило слоёв: **расчёты — в `lib/` чистыми функциями** (их покрывают тесты
vitest), **сторы хранят и сохраняют**, **хуки собирают данные для раздела**,
**страницы и компоненты только показывают**. Если два места показывают одно и
то же число, они зовут одну функцию из `lib/` — копия расчёта рано или поздно
разойдётся с оригиналом (пример — бюджет месяца: `lib/budgetMonth.ts` общий
для раздела «Бюджеты» и «Отчёта за период»).

## Хранение

- **`lib/db.ts`** — IndexedDB через `idb`, две таблицы:
  - `transactions` (ключ `id`) — операции, `saveTransactions` переписывает
    таблицу целиком. Поэтому после правок, черновиков и удалений — только
    `useDataStore.refresh` (накладка поверх таблицы); `reapplyRules`
    переписывает таблицу и нужен лишь при смене псевдонимов получателей;
  - `meta` — ключ → JSON: курсы (`rates`), сведения об импорте (`import`) и
    состояние каждого стора под своим ключом (`saveJSON` / `loadJSON`) — кэш
    Дзен-мани, токен, журнал синхронизаций, правила, настройки…
- **Кэш Дзен-мани в памяти** (`lib/zenCacheMemo.ts: getZenCache`) — один
  прочитанный объект на вкладку: чтение без разбора всего кэша из базы. Его
  только читают; кто собирает из кэша новый кэш или запись — берёт свежую
  копию `loadZenCache`. `saveZenCache` и `clearZenCache` сами сбрасывают его
  и список счетов (`onZenCacheWrite`), чужие вкладки — через `lib/crossTab`.
- **Несколько аккаунтов** (`lib/profiles.ts`): у каждого своя база —
  `dzenanalytics` для первого, `dzenanalytics-<id>` для остальных; список и
  активный — в `localStorage` (`dzenanalytics:profiles`,
  `dzenanalytics:activeProfile`). Переключение — перезагрузка страницы
  (`hooks/useProfiles.ts`). Данные аккаунта читаются только через `lib/db`.
- **Две вкладки одного аккаунта.** Стор пишет свой ключ целиком из памяти,
  поэтому вкладки договариваются: `lib/db` объявляет каждую запись через
  `lib/tabChannel.ts` (BroadcastChannel), а `lib/crossTab.ts` в остальных
  вкладках перечитывает изменившееся — очереди правок, кэш, состояние
  подключения, ленту. Настройки вида у вкладок свои и не перечитываются.
- **Демо** (`hooks/useDemo.ts`) — отдельный профиль «Семья (демо)»; ответы
  «API» для него собирает в браузере `lib/demo/demoServer.ts`, в сеть ничего не
  уходит. Выход из демо удаляет его базу.
- **Резервные копии** (`lib/backup.ts`, `store/useBackupStore.ts`) — файл со
  всеми данными и настройками по расписанию, без токена и кэша.
  Восстановление пишет всё одной транзакцией (`db.writeAll`).
  **Снимки облака** (`lib/cloudSnapshots.ts`) — полный ответ Дзен-мани перед
  отправкой правок (5 последних), для отката.

## Модель данных

`Transaction` (`src/types.ts`) — одна строка ленты: тип (`expense`, `income`,
`transfer`, `refund`), дата и время создания, категория и подкатегория (и
исходные — до правил), получатель и бренд, счёт и сумма каждой стороны, сумма
в базовой валюте `amountBase`, участник, признак «новая».

**`store/useDataStore.ts`** держит две версии ленты:

- `transactionsRaw` — после правил, без ручных правок (как в базе);
- `transactions` — то, что видно на экране.

Сборка ленты: пересчёт `amountBase` по курсам → группировка получателей →
сброс категорий к исходным → правила → `finalize`: наложить правки
(`lib/applyEdits.ts`), убрать удалённые, добавить черновики новых операций,
проставить ключи счетов, скрыть чужие операции в совместном доступе.

**Счёт — это ключ, а не название** (`lib/accountKey.ts`): у тёзок разные
ключи, подписи берутся из справочника (`hooks/useAccountDirectory.ts`).
Группировать по названию счёта нельзя.

## Синхронизация с Дзен-мани

Весь обмен — один эндпоинт `POST https://api.zenmoney.ru/v8/diff/` с токеном
(`lib/zenmoney.ts`: `fetchDiff`, `pushDiff`).

**Приём** — `useZenmoneyStore.sync`:

1. кэш (`lib/zenmoneyCache.ts`) хранит всё, что пришло: счета, валюты,
   категории (теги), получатели, операции, бюджеты, планы и их даты, сведения о
   пользователе; запрос — с `serverTimestamp`, то есть приходит только новое.
   Полная синхронизация — с нуля; при смене схемы кэша нужные сущности
   дозапрашиваются (`BACKFILL_BY_VERSION`);
2. ответ сливается с кэшем по id, с учётом удалённого. Пустой ответ
   (`isEmptyDiff`) дальше не идёт: кэш, лента, калибровка и бюджеты остаются,
   метка сервера тоже — справочники не перечитывают кэш впустую;
3. кэш превращается в ленту (`lib/zenmoneyMap.ts: mapZenmoneyDiff`): базовая
   валюта пользователя, тип операции по сторонам, переводы, возвраты, долги,
   «Без категории»;
4. дальше — категории, курсы, калибровка остатков, бюджеты и планы
   (`mirrorZenPlans`), журнал синхронизации, а в режиме «При синхронизации» —
   отправка правок.

Ошибки — с шагом и кодом HTTP (`lib/syncDiagnostics.ts`), журнал — 100
последних записей (`store/useSyncLogStore.ts`). Автосинхронизация проверяется
каждые 30 секунд, пока вкладка на виду.

**Вход.** Токен хранится в базе браузера. В сборке с параметрами
`VITE_OAUTH_PROVIDER_URL` и `VITE_OAUTH_CALLBACK_PATH` появляется кнопка «Войти
через Дзен-мани» (`lib/oauth.ts`): браузер уходит на провайдер, тот возвращает
код, панель меняет его на токен у провайдера. Без этих параметров (архив,
Docker) — поле для токена. В однофайловой сборке входа нет никогда.

**Курсы** (`lib/historicalRates.ts`). Суммы считаются по курсу ЦБ **на дату
операции**, как в Дзен-мани: курсы нужных дней подгружаются в фоне (около
запроса в секунду) и кэшируются; пока курса дня нет — текущий курс.

**Настройки между устройствами** (`lib/cloudSettings.ts`,
`store/useCloudSettingsStore.ts`). Свой сервер не нужен: настройки, правила,
цели, виды и разрезы лежат JSON-ом в комментариях служебных планов на
архивном счёте «DzenAnalytics Settings» в самом Дзен-мани. При каждой
синхронизации документы сливаются: поле — «кто записал позже», коллекции —
поэлементно. Удалить служебный счёт — значит выключить перенос.

**CSV и Excel.** CSV из Дзен-мани разбирает `lib/csv.ts` (заменить или
дополнить ленту). Шаблон Excel (`lib/importTemplate.ts`) заполняется и
загружается обратно (`lib/xlsxRead.ts`, `lib/importRows.ts`) — строки
становятся черновиками и уходят в Дзен-мани обычной отправкой.

## Правки и отправка в Дзен-мани

Правка не меняет данные сразу — она встаёт в очередь своего стора, и экран
показывает данные с наложенными правками.

| Стор | Что в очереди |
|---|---|
| `useEditsStore` | правки полей операций (и кто их сделал — человек или правило) |
| `useDraftsStore` | новые операции целиком |
| `useDeletedStore` + `useDeletedPayloadsStore` | удалённые и их копии для возврата |
| `useTagEditsStore`, `useNewCategoriesStore`, `useTagDeletionsStore` | категории |
| `useCounterpartyEditsStore` | получатели: переименования, новые, удаление, склейка |
| `useAccountEditsStore` | поля счетов (без остатка и валюты) |
| `useBudgetEditsStore` | планы бюджета по месяцам |
| `usePlanActionsStore`, `usePlannedDeletionsStore` | планы: «факт», «связать», перенос, удаление |

**Режим отправки** — «Выкл.» (по умолчанию), «Вручную», «Авто» (через 2 с
после последней правки), «При синхронизации». Всё отправляет одна функция
`useZenmoneyStore.pushPendingEdits`:

1. снимок облака (по умолчанию раз в день);
2. свежий ответ Дзен-мани и проверка конфликтов: операцию изменили в облаке
   после нашей синхронизации — правка остаётся в очереди;
3. сборка запроса чистыми функциями `lib/zenmoneyPush.ts` (`buildPushItems`,
   `buildDeletions`, `buildTagPush`, `buildBudgetPush`… — по одной на вид
   правки; удаление важнее правки той же строки). Версии одной операции из
   разных очередей складывает в одну запись `unifyPushTransactions`: спорное
   поле решает правка человека, ссылки на удаляемую категорию и объединяемого
   получателя заменяются;
4. один запрос `/v8/diff`;
5. ответ — в кэш, очереди чистятся, лента пересобирается, запись в журнал.

**Что снимается с очереди** (`lib/pushQueue.ts`): только то, что уехало как
есть. Запись, которую поправили, пока шёл запрос, остаётся и уходит следующей
отправкой. Правки, которым отправляться некуда (категория или счёт уже такие в
облаке, операции в Дзен-мани больше нет), снимаются сразу.

**Очерёдность** (`lib/zenLock.ts`): синхронизация и отправка идут строго по
очереди — внутри вкладки и, через замок браузера, между вкладками одного
аккаунта. Обе читают и переписывают один кэш; пойди они разом, последняя
запись затёрла бы чужую.

**Обратимость** (`lib/undoable.ts`, `lib/pushHold.ts`): действие выполняется
сразу, а в уведомлении — «Отменить»; пока оно на экране, «Авто» и «При
синхронизации» ждут. Отменённое удаление забирает и копию операции «для
возврата» — иначе операцию, удалённую позже в самом Дзен-мани, вернула бы
следующая отправка.

**Протоколы Дзен-мани**, которые надо знать:

- **время создания** операции нельзя поменять на месте — операция
  пересоздаётся под новым id, старая удаляется тем же запросом;
- **разделение** — все части новые, исходная удаляется (как делает само
  приложение); **объединение** — одна новая, исходные удаляются;
- **факт по плану** — операция со ссылкой на дату плана (`reminderMarker`),
  дата отмечается исполненной;
- **бюджет** уходит точными суммами с «замком» — Дзен-мани перестаёт добавлять к
  нему запланированные операции;
- **удалённое** в Дзен-мани не воскресить — «вернуть» значит создать копию
  (раздел «Удалённые»).

**Правила** (`lib/ruleEngine.ts`, `lib/rulePlan.ts`,
`store/useCategoryRulesStore.ts`) сами данные не меняют: всё, что меняет
правило, — обычная правка с пометкой «правило», и ручные правки они не
перезаписывают. Запускаются на новых операциях, по расписанию, кнопкой.

## Какие операции считаются в итогах

- **Ленты** («Операции», «Без категории»…) показывают всё.
- **Итоги и графики** берут `useInBalanceTransactions` — без счетов вне
  баланса (если они не включены в «Расчётах»), с переводами на кредиты как
  расходом — или `useAnalyticsTransactions`: то же плюс активный **разрез**
  (`store/useSlicesStore.ts`: исключённые категории и счета). Правило одно на
  все итоги (`lib/aggregations.ts: stripFromAnalytics`), отдельных фильтров-двойников
  нет. Срез считается раз на смену данных на всю вкладку, а не в каждом
  компоненте (`lib/memoLast.ts`); так же — выборки панели фильтров. Справочник
  счетов и список живых счетов не меняют объект, если состав тот же.
- **Отчётный месяц** — со своим первым днём (`store/useReportPeriodStore.ts`;
  по умолчанию — день из настроек Дзен-мани): «Август» с днём 28 — это
  28.08–27.09. Дзен-мани так считает всё, включая бюджеты.
- **Бюджет** — периметр счетов и правила «Планов» Дзен-мани
  (`hooks/useBudgetScope.ts`, `lib/budgetScope.ts`: какие переводы идут в
  бюджет, возвраты, входящий баланс), месяц целиком — `lib/budgetMonth.ts`,
  год — `lib/budgetYear.ts`.

## Интерфейс

**Оболочка.** `main.tsx` выбирает роутер: `BrowserRouter` для сайта и Docker,
`HashRouter` для однофайловой сборки и `file:`. Разделы грузятся сразу, без
ленивой подгрузки. `App.tsx` держит общие окна (палитра команд, шторка
операций, обучение, темы, подтверждения, уведомления), гидратирует сторы и
запускает фоновые таймеры: автоотправку, автосинхронизацию, правила по
расписанию, резервные копии.

**Шапка и разделы.** `TopNav` — шапка; основное меню настраивается
(`lib/headerNav.ts`), группы разделов — `lib/navSections.ts`. Каждый раздел
начинается с `PageHeader` (крошки «Группа / Раздел» и слот справа), настройки
раздела встают в этот слот через `SectionControls`. Переходы — только
`SmoothNavLink` / `useSmoothNavigate` (плавная смена через View Transitions).
Общие фильтры — `GlobalFilters` (`store/useFiltersStore.ts`), их можно
показывать панелью под шапкой (`FiltersDock`); сохранённые виды —
`useSavedViewsStore`.

**«Скрыть суммы»** (`store/usePrivacyStore.ts`): `formatMoney` обрамляет каждую
сумму невидимыми метками (`U+2060` … `U+2063`), по ним суммы прячутся на
экране; при копировании и выгрузке метки снимает `stripAmountMarks`.

**Общие компоненты.** Одинаковое делается одним компонентом, без копий
разметки:

| Что | Компонент |
|---|---|
| Таблицы (сортировка, CSV, своя ширина столбцов) | `DataTable` (`components/table/tableKit.ts`) |
| Окна | `Modal`, `ModalHeader`, `ModalBody`, `ModalFooter` |
| Выбор из списка | `Combobox`, `Select`, `MultiSelect`; категория — всегда `CategoryCascadePicker` (внутри прокрутки — с `portal`) |
| Переключатели, бегунки | `Segmented`, `Switch`, `Slider` |
| Подсказки графиков | `ChartTooltipCard` + `TooltipFacts` |
| Плитки итогов | `StatCell`, `StatRow` (`SectionCard.tsx`) |
| Отклонения | `DeviationPill`, `DiffModeToggle` (₽ → % → ₽ %) |
| Выбор формата выгрузки | `FormatChoice` |

Системных подсказок браузера нет: каждый `title` перехватывает
`lib/nativeTooltips.ts` и показывает свою.

**Темы.** 6 светлых и 6 тёмных тем плюс своя
(`lib/themeSchemes.ts`, `lib/customTheme.ts`): тема — атрибут
`data-scheme` на `<html>`, цвета — переменные `--c-*` в `src/index.css`,
Tailwind берёт их через `rgb(var(--c-*))` (`tailwind.config.js`). Радиусы —
только токенами `rounded-control*` / `rounded-track*`, движение — `--motion-*`.

**Справка и обучение.** Справка — `pages/HelpPage.tsx` (разделы `page-*`,
поиск по тексту, «Что нового» из `CHANGELOG.md`). Обучение — главы в
`lib/tour.ts`, подсветка элементов по `data-tour`.

## Выгрузки

- **PDF** — снимки свёрстанных листов (`html-to-image`) в свой минимальный PDF
  (`lib/budgetPdf.ts`, `lib/pdf.ts`), кириллица и шрифт всегда на месте.
- **Excel** — `write-excel-file`, а чего он не умеет (диаграммы, формулы,
  выпадающие списки, группировка строк, примечания) — дописывается в готовый
  файл (`lib/xlsxCharts.ts`, `xlsxFormulas.ts`, `xlsxNotes.ts`): xlsx — zip с
  XML, патч считает правки и падает, если нашёл не все.
- **HTML** — самостоятельная страница из тех же листов, что PDF, со шрифтом
  внутри (`lib/periodReportExport.ts`).
- **CSV** — из любой `DataTable` (разделитель `;`, BOM).

Библиотеки выгрузок подгружаются только по кнопке.

## Тесты

- **vitest** (`npm test`) — чистая логика: ~140 файлов `*.test.ts` рядом с кодом
  в `src/lib` и `src/store`. Окружение node без jsdom: хуки и компоненты здесь не
  проверить — это задача e2e. Заготовки — `src/test/fixtures.ts`.
- **Playwright** (`npm run test:e2e`) — ~70 сценариев `e2e/*.e2e.ts` в Chrome на
  своём сервере (порт 3131). `e2e/harness.ts` подменяет Дзен-мани
  (`FakeZen`: принимает запросы, запоминает отправленное) и курсы ЦБ, режет
  остальную сеть, останавливает часы на 15.10.2026 и открывает сторы через
  `window.__store(name)`.
- **CI** (`.github/workflows/ci.yml`) — vitest, обе сборки и линтер (для
  сведения). e2e запускаются локально.

## Сборка и выпуск

- `npm run dev` — сервер разработки на 3030 (`POST /_devlog` пишет журнал
  приложения в `dev-logs/app.log`).
- `npm run build` — `tsc -b && vite build` → `dist/`. Параметры сборки:
  `APP_BASE` (путь, если не в корне сайта), `VITE_OAUTH_*` (вход через
  Дзен-мани). Версия — из `package.json` (`__APP_VERSION__`).
- `npm run build:standalone` — `STANDALONE=1`: один HTML со всем внутри
  (`vite-plugin-singlefile`), адреса разделов после `#`, без service worker.
- `npm run release:zip` — чистая однофайловая сборка → архив с
  `DzenAnalytics.html`, `README.txt` и `THIRD-PARTY-LICENSES.txt`.
- **Лицензии библиотек** — `scripts/thirdPartyLicenses.ts`: при каждой сборке
  пакеты из графа модулей → `THIRD-PARTY-LICENSES.txt` с полными текстами.
- **Docker** — `docker/Dockerfile`: сборка на Node, раздача nginx
  (`docker/nginx.conf`: ассеты — на год, страница — без кэша). Образ
  `ghcr.io/deadover/dzenanalytics` собирается сам по опубликованному релизу
  (`.github/workflows/docker-publish.yml`, amd64 + arm64).
- **Service worker** (`public/sw.js`) — страница сначала из сети (свежий код),
  остальное — из кэша; только в обычной сборке.
- **Релиз** — версия `X.Y.Z` (Y — новое, Z — только исправления), запись в
  `CHANGELOG.md` в формате `## vX.Y.Z — Название · ГГГГ-ММ-ДД` (её читают
  `scripts/release-notes.js` и справка), GitHub Release с архивом.

## Известные хвосты

- `store/useAnalyticsExclusionStore.ts` нигде не используется — его заменили
  разрезы; ключ живёт только для переноса старых настроек.
- Комментарии в `lib/splitTransaction.ts` и `store/useSplitGroupsStore.ts`
  описывают старое разделение («исходная ужимается до первой части»); на деле
  все части новые, а исходная удаляется.
- Комментарий в шапке `store/useSlicesStore.ts` говорит, что разрезы в облако
  не уходят, — они переносятся вместе с настройками.
- Проверка конфликтов перед отправкой смотрит только операции, не категории,
  бюджеты и счета, и только изменения с последней записи кэша: у правки нет
  метки версии, от которой она сделана. Саму `pushPendingEdits` покрывают e2e,
  модульного теста у неё нет.
- `db.loadJSON` отдаёт `null` вместо сохранённых `false` и `0`; все нынешние
  вызовы к этому устойчивы (`=== true`, значения по умолчанию).
